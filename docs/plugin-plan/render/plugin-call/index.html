Plugin forwarding - Index

When a renderer component needs its own plugin's private data: dispatch("plugin.call"). The chain is dispatch -> validate the declaration -> forward across processes -> the plugin answers -> JSON comes back. One question, one answer; no streaming. This is a render interface, not a UI slot.

Why there is no demo

Interface-only, so the demo is omitted. This folder pins the forwarding contract and the failure codes; there is no mountable UI slot. How a slot component draws the data it fetched is covered by that slot's own demo; this folder only guarantees how the data is fetched.

Summary

  • Chain: the component calls dispatch("plugin.call") -> the declaration is validated -> the cross-process plugin/renderer/call ({pluginId, method, args}) -> the plugin's own onRendererCall -> a JSON answer.
  • pluginId is injected by the host and cannot be self-supplied - a plugin can only call itself and cannot impersonate another.
  • Five constraints: a method allowlist, a payload cap of 64KB, a QPS rate limit, a 2s timeout, and a circuit breaker on consecutive failures, PLUGIN_CALL_DISABLED.
  • Failure codes: PLUGIN_CALL_NO_HANDLER - UNSERIALIZABLE - TIMEOUT - ...
  • No streaming - one question yields one answer, and the return value must be JSON-serializable.
  • Outbound layering: core P.

Open questions

The exact QPS value and the consecutive-failure threshold for the circuit breaker are open - see "Open questions" in data-flow.html.
