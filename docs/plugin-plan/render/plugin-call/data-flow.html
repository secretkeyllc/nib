Plugin forwarding - Data flow

One plugin.call round trip: the component initiates, the host validates and injects identity, the call crosses processes to the plugin, and JSON comes back. Six fixed sections: API contract / how data flows / error handling / what is not provided / related entries / open questions.

status: draft - issue #545 - #561 - outbound layering: core P - field names are proposals

1API contract Decided

One renderer action, plugin.call, in the core P tier of the outbound layering. One question, one JSON answer, no streaming.

// component side
const data = await dispatch("plugin.call", { method, args })

// cross-process payload (assembled by the host; pluginId cannot be self-supplied)
IPC plugin/renderer/call
  { pluginId, method, args }

// plugin side
onRendererCall(method, args) → JSON value

Boundary in one sentence.F = a synchronous pure function on the renderer thread; H/P = asynchronous cross-process dispatch. plugin.call is P - slow, fallible, and rate-limited; it must never be called inside F.

2How data flows Decided

host host validation / forwarding slot interface boundary plugin slot component / this plugin's main
  1. dispatch - the slot component issues dispatch("plugin.call", { method, args }). There is no pluginId here.
  2. Validate the declaration - the host asks: is the method on the allowlist? Is the payload over 64KB? Over QPS? Is the breaker tripped? If any answer fails, it returns the failure code immediately without going further.
  3. Forward across processes - the host assembles the IPC plugin/renderer/call { pluginId, method, args }. pluginId is injected by the host; a component cannot fill it in.
  4. The plugin answers - that plugin's onRendererCall(method, args) runs and produces a JSON value.
  5. JSON comes back - the answer returns the same way to the component's await and settles as that JSON value; if it does not arrive within 2s -> TIMEOUT.

Delivery model

  • Request / response, one round trip at a time. It is neither a subscription nor a stream.
  • Identity flows one way: only the host injects pluginId, and the component side can neither see nor write it.
  • One direction: component -> its own main. The reverse (main pushing to a component) does not use this interface.
  • Lifetime: it follows the plugin. On unload, pending calls settle with a failure code instead of hanging.

Failures are never silent.Every rejection returns a code so the caller can tell "no such method" from "too slow" from "the breaker tripped". A P result must never silently change user data - the answer is data only, and side effects go through H verbs.

4What is not provided Settled

6Open questions

  • The exact QPS value (per plugin or per session).
  • The consecutive-failure threshold for the circuit breaker, its cooldown, and how it recovers.
  • Whether the 64KB cap is one-way or the two directions combined.
  • Whether every failure code carries the PLUGIN_CALL_ prefix (the current examples do).
