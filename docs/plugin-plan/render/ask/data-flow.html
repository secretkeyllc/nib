Confirmation card - Data flow

One ui.ask round trip: the plugin initiates, the host queues the card, the user presses a button, the result settles. Six fixed sections: API contract / how data flows / error handling / what is not provided / related entries / open questions.

status: draft - issue #545 - #561 - field names are proposals; the structure is decided

1API contract Decided

One renderer interface, ui.ask, in the optional H tier of the outbound layering. The return is always an object.

// inside the plugin renderer
const { choice, reason } = await pi.ui.ask({
  title, description?, actions: [{ id, label, variant? }]
})
// choice = id of the pressed button
// reason = present only for abnormal dismissal, e.g. "plugin-unloaded"

Return shape (fixed)

casereturn
The user presses a button{ choice: "<actionId>" }
Plugin disabled / unloaded{ choice: "cancel", reason: "plugin-unloaded" }
String-or-object returns are forbidden. The old contract sometimes returned the button id as a string and sometimes an object on unload, forcing callers to write two branches. Everything is { choice, reason? } now.

2How data flows Decided

host host confirmation card slot interface boundary plugin plugin renderer
momentwhowhat happens
CallPluginawait pi.ui.ask(...); once the arguments validate, the card enters the host queue
QueueingHostPlugin confirmation cards are first in, first out; a permission approval card jumps the queue at any time (security first, not a fair queue)
On screenHostWhen its turn comes, the fixed shell appears as a full-width bar above the composer; title, description, and buttons are laid out from the arguments
While shownHostThe content is fixed; no plugin code runs inside the card
ClickUser → hostA button is pressed -> the card is removed -> the Promise settles with { choice } -> the next card appears
UnloadHostPlugin disabled / unloaded -> cards (including queued ones) are removed and the pending await settles with { choice:"cancel", reason:"plugin-unloaded" }
One narrow return path. Only "button id plus optional reason" travels back to the plugin; the card receives no session content and the plugin receives no card internals.

3Error handling Settled

caseresultguaranteed by
Invalid call argumentsThe call is rejected with an error code (too many buttons, missing fields) and no card is createdInput validation
Plugin disabled / unloadedCards are removed; pending waits settle with { choice:"cancel", reason:"plugin-unloaded" }Plugin lifecycle cleanup
A permission card jumps the queueThe plugin card returns to the queue and resumes in its original order afterwardsSecurity-first queue rules
The user never presses anythingNo timeout and no Esc handling; the promise settles only on a click or an unloadCard lifecycle

4What is not provided Settled

not providedwhy
Taking over or redrawing the host permission approval cardThe security decision surface belongs to the host only; ui.ask never enters the permission decision path
Custom drawing or components inside the cardThe content is fixed fields only; no plugin code runs inside the card
A string returnTwo states are forbidden; always { choice, reason? }
A layer mechanism, registration, or arbitrationThe confirmation card is not a UI slot
Session or message dataThe card only asks the user a question
Sharing a shape with the agent-side boolean confirmationSame name, different thing: that one is an allow / deny boolean, this one is a button-choice object
