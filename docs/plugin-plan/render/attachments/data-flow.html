Attachments - Data flow

How content reaches the staging area, how the list is filtered by origin, and how removal is confined to the plugin's own entries. Six fixed sections: API contract / how data flows / error handling / what is not provided / related entries / open questions.

status: draft - issue #545 - #561 - S1 red line: no path / file:// / URL references

1API contract Decided

Three actions. add accepts content or a token only; list / remove are confined to the plugin's own entries.

// (1) add
attachments.add({ name, mimeType, content | token })
// → { id }

// (2) list - only its own entries
attachments.list()
// → [{ id, name, mimeType, size }]

// (3) remove - only its own entries
attachments.remove(id)
// → { ok: true }

Fields

fieldmeaning
nameDisplay name; the extension is required
mimeTypeType; decides between a thumbnail and a file chip
content | tokenExactly one: the content itself, or a content token the host recognizes
idAllocated when the host registers the entry; removal and references both use it
The S1 red line lands in the rejected layer. Any path / file:// / URL reference is refused; a bare-path attachment never reaches the staging area.

2How data flows Decided

host staging area / attachment registry slot action boundary plugin plugin renderer
pathdirectionhow it travels
addplugin → hostHand over { name, mimeType, content|token } -> the host validates (rejects paths, rejects missing extensions) -> stages it -> allocates an id and returns it
listhost → pluginFiltered by origin: only the entries this plugin added are returned
removeplugin → hostValidates id ownership: only its own are deleted; otherwise -> rejected and the list is unchanged
sendhostAt send time the host pulls the content from the staging area and it travels as a normal attachment
clearhostSwitching or deleting a session clears both the staging area and the registry

How ownership is recorded

  • Every attachment records one origin: the user, or a specific plugin.
  • Both the list filter and the remove gate key off that origin marker.
  • The origin marker is injected by the host and cannot be self-supplied; otherwise a plugin could impersonate another and touch its entries.
Staging-area lifetime.It follows the session: switching empties it and deleting the session removes it. After handing content over, the plugin holds no address; the old "plugin stores its own copy, registers only a ref" model is retired (that route offloaded the responsibility of reading the disk or network onto the host).

6Open questions

  • The exact form of the token: a one-time credential, a host handle, or something else.
  • Per-entry and total staging-area caps, and the error code when they are exceeded.
  • Whether a plugin's attachments survive unload until send (currently: they stay in the staging area and follow the session).
