Attachments - Index

Three attachment-area actions: attachments.add / attachments.list / attachments.remove. They accept content or a token, never an address; the host moves the content into a staging area; each plugin sees and touches only its own. This is a render interface, not a UI slot.

Why there is no demo

Interface-only, so the demo is omitted. This folder pins the input and the boundaries; there is no mountable UI slot. For what the attachment area looks like, see ui/composer/demo.html (scenario 6: add / list / remove); the UI is not repeated here.

Summary

  • There are only three inputs: { name, mimeType, content|token } - a name, a type, and either the content itself or a token that fetches it.
  • S1 red line: no path / file:// / URL references. A plugin may not hand over an address and let the host read the disk or the network; a bare-path attachment is rejected outright.
  • The host moves the content into the staging area; the plugin no longer keeps an address of its own.
  • list shows only what this plugin added; remove touches only what this plugin added. Neither the user's nor another plugin's entries are reachable.
  • Outbound layering: attachments.add is core H; list / remove are optional H; bare-path attachments are rejected.

Open questions

The exact form of the token (a one-time credential or a host handle) and the staging-area size cap are open - see "Open questions" in data-flow.html.
