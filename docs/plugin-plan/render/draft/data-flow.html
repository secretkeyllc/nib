Draft read/write - Data flow

How the draft snapshot is read, how text is written back, and how changes are pushed to plugins. Six fixed sections: API contract / how data flows / error handling / what is not provided / related entries / open questions.

status: draft - issue #545 - #561 - field names are proposals; the structure is decided

1API contract Decided

Three methods; writing splits into a primary path and a restricted path. Draft changes arrive by push.

// (1) read the snapshot
composer.readDraft()
// → { text, marks[], generation }

// (2) insert (primary path)
composer.insertText({ text })
// → { ok: true, generation }

// (3) whole replacement (restricted: CAS + unfocused + non-remote)
composer.replaceDraft({ expectedGeneration, text, marks? })
// -> { ok: true, generation }, or the whole call is rejected

Fields

fieldmeaning
textThe composer's current text; tokens occupy characters within it
marks[]The token list (label / send policy / private data / position), in order of appearance
generationThe draft generation; increments on every change. replace reconciles against expectedGeneration
expectedGenerationPresent only on replaceDraft: must equal the current value, or the whole call is rejected

The three replace gates

gatewhat happens if it fails
(1) CAS generationexpectedGeneration != current -> the whole call is rejected (first writer wins; no silent overwrite)
(2) Composer unfocusedThe user is typing in the composer -> rejected (so their text is not eaten)
(3) Not a remote originThe call comes from an async callback, a network response, or a timer -> rejected; use insertText instead

2How data flows Decided

host composer / draft registry slot method boundary plugin plugin renderer
pathdirectionhow it travels
readplugin -> host -> pluginreadDraft() synchronously takes a { text, marks[], generation } snapshot
insertplugin -> hostinsertText places a run of text at the caret; on success generation increments
replaceplugin -> hostreplaceDraft swaps the whole draft once past the three gates; on success generation increments
pushhost -> pluginWhenever the draft changes (user typing, edits, a plugin write), rendererData draft pushes a new snapshot. Do not poll

Delivery model

  • Request / response: all three methods are one question, one answer, and the return settles immediately.
  • Push: draft changes travel one way from the host; a plugin subscribes to rendererData draft. Timed pulls are neither needed nor offered.
  • Lifetime: it follows the session. After a switch the old snapshot is invalid and the new session's pushes take over.
Why not polling.Polling alongside pushing creates two sources, and a plugin listening to both ends up in conflict; polling is also always one beat late. Decision: push only, never pull.
