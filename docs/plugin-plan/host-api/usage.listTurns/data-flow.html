1Interface contract

pi.usage.listTurns(input?: { fromMs?: number; toMs?: number; projectId?: number | null; sessionId?: string; cursor?: string; limit?: number }): Promise<PluginUsageTurnPage>

Reads usage fact rows for completed turns, paginated (token counts and identifiers, read-only, no message bodies). Permission: —.

Inputs

FieldTypeRequiredDescription
fromMsnumberNoWindow start, epoch ms (inclusive); defaults to toMs − 30 days.
toMsnumberNoWindow end, epoch ms (inclusive); defaults to now; window span ≤ 365 days.
projectIdnumber | nullNoOnly one persistent project.
sessionIdstringNoOnly one session.
cursorstringNoThe nextCursor returned by the previous page (opaque, pass it back as-is).
limitnumberNoRows per page, 1..=500; default 200.

Outputs

Element structure: turnId, sessionId, sessionTitle (string|null), projectId (number|null), providerId (string|null), modelId (string|null), startedAt, endedAt (epoch ms), inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, reasoningTokens.
nextCursorstring | nullCursor for the next page; null means the window has been fully read.

2How data flows

  1. Call: the plugin provides the window (fromMs / toMs), filters (projectId / sessionId), cursor, and limit.
  2. Validation: requires the usage.read permission; window span ≤ 365 days and limit 1..=500, otherwise INVALID_ARGUMENT.
  3. Execution: the host does keyset pagination over the usage fact table (turns.usage_json), ordered by endedAt ascending.
  4. Return: turns + nextCursor; a null cursor means everything has been read.
DirectionContent
plugin → hostWindow / filter / pagination parameters.
host → pluginA page of usage fact rows { turns, nextCursor }.
Recommended pattern (capability list N2 closed: no new push API).Events are broadcast only after usage is committed to the database (the main process first awaits session.endTurn to commit the write, then broadcasts session:turnEnded), so listening to session:turnEnded as a signal and then pulling this API incrementally with the cursor is accurate: missed events can be backfilled in full, and the numbers share the same source as the host usage page.
Host pipeline (official RPC).In-turn usage accumulation → turn-end RPC session.endTurn → host-core transactionally writes the turns table → broadcasts session:turnEnded; read side: plugin usage.listTurns → main process checks usage.read → plugin.usage.listTurns → host-core plugin_usage::list_turns_page → SQLite turns (keyset: ended_at, id ascending).
