1Interface contract

pi.net.websocket.connect(input: PluginWebSocketConnectInput): Promise<{ socketId: string }>

Connects to a ws:// / wss:// endpoint and returns a socket handle (permission: —; domain constraints share the same manifest.net.domains as net.fetch).

Input

FieldTypeRequiredDescription
urlstringYesAbsolute ws:// / wss:// address; the host must be in manifest.net.domains.
headersRecord<string, string>NoHandshake request headers as key-value pairs.
protocolsstring[]NoWebSocket subprotocol list.
timeoutMsnumberNoHandshake timeout in milliseconds.

Output

FieldTypeDescription
socketIdstringHandle for the new connection; later send / close calls and open / message / close / error events are identified by it.

Input example

{ "url": "wss://rt.example.com/feed", "protocols": ["v1.json"], "timeoutMs": 5000 }

Output example

{ "socketId": "ws-a1b2c3" }
Boundary in one line. Off-allowlist hosts never reach the transport layer and no native socket handles are given; at most 4 connections per plugin, frames capped at 1 MiB, and the host closes them all when the plugin unloads.

2How data flows

  1. Call: the plugin process passes { url, headers?, protocols?, timeoutMs? }.
  2. Validate: only ws:// / wss:// are accepted, and the hostname must match manifest.net.domains (the same allowlist as net.fetch), otherwise PERMISSION_DENIED; ws:// is just the plaintext form of http and is not a looser channel.
  3. Execute: the host establishes and holds the underlying socket (max 4 per plugin); the plugin only gets a socketId.
  4. Afterwards: open and message arrive as events (PluginWebSocketOpenEvent / PluginWebSocketMessageEvent); when the plugin unloads / is disabled / crashes, the host closes all of its sockets.
