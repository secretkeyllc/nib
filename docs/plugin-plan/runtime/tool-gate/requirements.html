tool-gate · Requirements

Observation and blocking at the tool layer: a call can be blocked before it runs, and its result inspected after. Changing arguments is permanently excluded.

status: draft · issue #561 · permission runtime.tool.gate · budget 30s · changing arguments permanently excluded

Scope Verified

  • Only observation and blocking on the tool lifecycle: before the call, and after the result.
  • Out of scope: registering new tools (tool-extend), changing arguments (permanently excluded), intercepting sends (before-send).

Slow confirmation is the plugin's UI duty. To "ask the user before running": draw your own UI (a self-managed dialog), and after the decision handle it through the two-phase runtime.turn.continue path - you may not wait inside the gate for more than 30 seconds.

Explicit non-goals Verified

  • No changing arguments - permanently excluded, including wrapper workarounds (ADR 0303).
  • No changing the body of a tool result - after the result it is read-only.
  • No waiting inside the gate for a slow confirmation.
  • No registering new tools - that is tool-extend.
