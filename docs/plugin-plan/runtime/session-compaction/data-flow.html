1API contract

pi.session.applyCompaction(input: { sessionId: string; summary: string; retainedMessageIds?: string[]; reason?: string }): Promise<PluginApplyCompactionResult>

Hands a compaction summary computed by the plugin to the host for a managed write-back. Permission session.compact.write (new · high · confirmed at install · the operation is visible in the UI).

Input

FieldTypeRequiredNotes
sessionIdstringYesTarget session.
summarystringYesNon-empty plain text; HTML is not allowed; if too long it is rejected with LIMIT_EXCEEDED.
retainedMessageIdsstring[]NoIds of original messages to keep; the default means summary only. All of them must belong to this session.
reasonstringNoAudit tag, e.g. "diy-summarizer"; stored and shown with the compaction record.

Output

FieldTypeNotes
compactionIdstringId of the newly created compaction record.
tokensBeforenumberToken estimate for the working set before compaction.
tokensAfternumberToken estimate after compaction.
appliedAtnumberApplication timestamp (milliseconds); used for auditing and ordering.

Boundary in one sentence.A plugin never modifies the message list directly; the host manages the write-back into a compaction record, visible in the UI and carrying a source stamp - never a silent rewrite. Once the promise resolves the change is in effect (visible to the next request).

2How data flows

  1. Submit. The plugin passes { sessionId, summary, retainedMessageIds?, reason? }.
  2. Validate. The main process checks the session.compact.write permission, that summary is non-empty plain text, and that all retained ids belong to this session.
  3. Write. Goes through the host's existing session.appendCompaction RPC: shape validation, de-duplication by id, and the compaction record is stored; the main process injects the pluginId as the source stamp (recording "compacted by plugin X").
  4. Visible. The UI shows a compaction row (the renderer already renders compaction records); the audit trail is queryable.
  5. Effective. When the next request rebuilds its context, the summary plus the retained tail enter the LLM's view.
directioncontent
plugin → hostThe compaction submission (summary, retained list, audit tag).
host → storageThe compaction record is persisted (CompactionRecord).
host → pluginThe application result (compactionId, tokens before and after, timestamp).

4What is not provided

not providedwhy
replaceMessages / silent overwriteExcluded by the product; a write-back must become a compaction record, be visible in the UI, and be auditable
Deleting / editing messagesThis interface only does "summary plus retain" and touches no message row
Undo / rollbackNot in v1; the compaction row is visible and auditable, and rollback is left to a later version
HTML / rich-text summaryPlain text only, to prevent injection and UI styling breakage
