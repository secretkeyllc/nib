session.applyCompaction · Requirements

status: draft · design draft · session data contract · planned from: capability inventory review N4 · permission session.compact.write (new) · no SDK implementation yet

1Purpose and scope

Hands a compaction summary computed by the plugin to the host for a managed write-back: the host validates it and writes a compaction record (on the existing session.appendCompaction chain), the UI shows a compaction row, and it takes effect on the next turn. A plugin never modifies the message list directly.

pi.session.applyCompaction(input: { sessionId: string; summary: string; retainedMessageIds?: string[]; reason?: string }): Promise<PluginApplyCompactionResult>

Permission: session.compact.write (new · high · confirmed at install · the operation is visible in the UI and auditable).

2Typical scenarios

scenariowhat the plugin does
DIY compactor (primary scenario)Reads the working set with session.getContext → computes its own summary (e.g. via agent.complete) → submits it through this interface for write-back.
Domain compactionCompact using domain knowledge (keep code blocks in code discussions, keep conclusions from long documents), which saves more tokens than a generic summary.
User-triggeredThe plugin panel offers a "compact now" button so the user can slim the conversation down on demand.

3Explicit non-goals

No silent rewriting: replaceMessages is not provided, and a summary must become a compaction record, be visible in the UI, and carry a source stamp. No undo/rollback (v1; the compaction row is visible and auditable, and rollback is left to a later version). summary accepts plain text only.

4Decided

  • Open a new permission domain, session.compact.write (high, confirmed at install); no second confirmation dialog - visibility in the UI plus auditing is the safety net.
  • Implementation anchor: the host's existing session.appendCompaction RPC (already does shape validation, de-duplicates by id, and takes effect on the next request); the main process injects the pluginId as the source stamp.
  • Concurrency conflicts are reported explicitly as CONFLICT, using compactionCursor from session.getContext for optimistic checking.
